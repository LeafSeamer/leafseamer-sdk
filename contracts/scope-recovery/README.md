# 出口所有者与持久拒绝恢复

本包接续 [局部释放门](../scope-release/README.md)，增加同机进程独占、同库拒绝意图和启动恢复。候选为 `approved=false`、`runtime_ready=false`，保持固定 SDK 来源及原协议字节。真实子进程终止已纳入本轮检查；系统崩溃、掉电、跨机器所有者和产品传输仍未验收。

## 所有者与固定锁根

[Owner](owner.py) 在建立任何可用 Gate 之前取得进程文件锁。锁名由发布服务、数据库实例和角色的完整身份派生，不包含每次变化的 owner epoch；改变 epoch 不能另开并行出口。锁句柄不可继承，退出时关闭但不删除锁文件，避免不同进程锁住不同文件实体。

初始化时把规范锁根路径的摘要固定到 `rg_configuration`。后续启动必须匹配该值；另选一个目录不能绕过同一库的配置。锁根必须是同一机器上受管理的稳定目录，身份和目录由可信启动配置提供，不能由远端请求选择。配置不提供原地改写／迁移接口；备份恢复及跨机器复制必须按完整库实例和运行域政策另行处理。

本机检查在 Windows 上实际使用进程文件锁并验证第二进程被拒绝。代码包含 POSIX 分支，当前未执行 Linux 验收。文件锁只约束遵循此入口并使用受管理锁根的进程；不防御有权限删除锁文件、篡改配置或绕过该入口的本机程序，也不证明另一台机器上没有克隆库。生产监督器、目录权限和全部可写出口仍须统一接线。

## 同库账本与启动顺序

[五表布局](recovery.sql) 附加到原七表注册库：

| 表 | 保存事实 |
| --- | --- |
| `rg_configuration` | 布局版本及固定锁根摘要 |
| `rg_session` | 不复用的 owner epoch 和启动顺序 |
| `rg_stop` | 门已关闭后的正常停止记录 |
| `rg_deny` | 原操作身份、完整规范请求和摘要、目标原件及登记 owner |
| `rg_recovery` | 被接替 owner、恢复 owner 和完整旧注册库存及摘要 |

五表禁止 UPDATE、DELETE 和 REPLACE；连接沿用已验证的外键、递归触发器与 FULL 同步配置。完整正文、列值、原件引用、库存唯一性及每项拒绝记录在应用层验证，外键检查只负责其声明的关系，不能冒充完整语义证明。

启动持有独占锁，在同一个新 writer 事务中校验历史库存、登记新 session、识别没有正常停止或恢复记录的旧 owner，并为当时全部注册对象写入永久恢复阻断，再封存完整库存。任一旧对象遗漏即拒绝启动且整库回滚，不能只加载前 N 项。候选最多接纳 10000 个历史注册对象，超过则保持关闭；该上限尚未经过产品容量批准。

事务完成后才创建 Gate，并将所有持久拒绝重新装入门内，再暴露开门接口。旧句柄、队列和传输身份不恢复。owner epoch 重用、配置不符、库存关系错误或来源漂移均不能得到可用出口。

## 撤销及原操作查原

`revoke` 的顺序为：验证目标原件 → 本机关门并清队列 → 提交完整持久拒绝意图 → 执行原注册撤销写集。这是两个有明确先后关系的提交，不宣称跨提交原子。原撤销暂时失败时，持久意图足以让后续 owner 继续拒绝该注册身份。

意图提交前故障或提交观察丢失会停止整个当前 owner，且不写正常停止记录。此时无法证明仅某个目标需要继续阻断，下次启动按未正常停止恢复处理，保守覆盖所有旧注册。已经提交的意图、原注册写集失败和正常停机可以并存，启动仍加载该意图，不能因正常停止而清掉墓碑。

`reconcile` 只按保存的原操作 ID 和完整正文查原或补交注册撤销，不新建操作身份。查原结果必须匹配原请求摘要；如果对象已由另一操作撤销，返回实际获胜操作的事实，不伪造本操作提交成功。冲突或恢复错误停止 owner。该重试适用于幂等的拒绝操作，不能用于设备动作重放。

## 未正常停止后的重新批准

未正常停止的恢复阻断保留所有旧注册的历史正文，但禁止这些身份再次开门。重新运行要求独立可信批准提供新的 Profile／Selector 身份或修订，并经过新连接、当前权限及发布资格核验；不改写旧墓碑，也不因重新计算摘要就复活旧对象。

这种保守策略会使进程异常退出后的现有订阅需要重新建立。它不能把网络中已交付字节撤回，也不证明已产生的设备作用不存在。当前检查验证了新的合成批准身份可以建立新连接；真实批准服务、订阅发送／ACK 状态和恢复用户流程仍需归并。

正常停止先关闭 Gate，等待门内已有出口调用结束，再提交停止记录并释放锁。停止记录写入失败时保持未正常停止状态；新 owner 使用上述恢复流程。模型的数据库调用由单一 owner 执行线程编排，不允许把同一 SQLite 连接交给多个线程并发使用。

## 验证与剩余范围

[检查器](check.py) 创建六个临时 SQLite 文件，验证同进程与实际第二进程竞争、锁根错配、超过260字符的锁路径、epoch 不复用、持久意图查原、提交故障、恢复漏项整库回滚、全部账本不可变约束及新批准身份。锁文件在 Windows 使用扩展路径进行文件操作，配置仍绑定规范逻辑根；长路径处理不得改变锁身份。检查器只强制结束自己创建并确认仍存活的两个合成子进程：一个持有活动 owner，另一个已经提交拒绝意图但尚未提交原注册撤销。随后核对锁可接替、旧 Scope 仍被拒绝，以及原操作可以查原补交。

```text
python -I -B contracts/scope-recovery/check.py
python -I -B contracts/scope-recovery/check.py --report
python -I -B contracts/scope-recovery/check.py --check-report
```

临时文件默认写入忽略的 `logs/scope-recovery-tests/`，`--work` 可指定尚不存在的目录。子进程启动和等待都有期限；`--check-report` 只检查输入摘要。报告分列 Windows 进程／SQLite 证据和未执行的平台、设备、认证、产品传输及掉电检查。
